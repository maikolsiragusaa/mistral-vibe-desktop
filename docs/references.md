# Architecture references

Research snapshot: 2026-10-12. This is an architecture comparison, not a recommendation to reuse or vendor another agent harness. Pin links below identify the reviewed upstream snapshots; product documentation links provide the corresponding concepts and current usage guidance.

## Decision for this app

Keep Mistral Vibe as the single owner of agent execution, tools, permissions, context, session history, and persistence. Build a thin Windows desktop client on Vibe's public `vibe-app-server` JSON-RPC boundary over stdio, using protocol definitions from the pinned Vibe source. Do not parse TUI text, manipulate Vibe's session files directly, or create a second agent/session manager. Keep the app's unique scope to workspace and trust UX, process lifecycle and diagnostics, session discovery/resume, streamed conversation display, queue/interrupt state, and Vibe approval/question callbacks.

Vibe already supplies agent modes and subagents, tool permissions, workspace trust, MCP/connectors, skills/hooks, session logging and resume, and context compaction. The desktop contributes delivery and Windows lifecycle. Preserve Vibe's permission decisions and configured default agent mode in the UI. For a missing event watermark or reconnect, reload canonical session state through the protocol. A reattached client can recover current runtime callbacks; a restarted app-server resumes durable history while its former in-flight turn, retry state and transient prompt queue are gone. Show the interruption and offer resume from saved history.

The Electron recommendation is specific to the current development setup: Node/npm are available, Rust/Cargo are not. Electron is directly buildable with the existing JS toolchain and the upstream desktop references demonstrate the sidecar pattern. Tauri 2 remains a possible later choice if a smaller native shell justifies adding Rust stable/MSVC and the Windows C++ build workload. Vibe's official Windows posture is less mature than its Unix target, so keep the server on stdio, verify the Windows packaged runtime and subprocess dependencies, and avoid its experimental Unix-domain agent socket.

## What the comparisons support

**Vibe: use its boundary, not its implementation details as a parallel API.** [ADR 0009, App Server Boundary](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/docs/adr/0009-app-server-boundary.md) defines the app-server as the delivery-surface runtime boundary, with session/config/credentials/tools/permissions/plugins/persistence and effect execution owned by the server. Its clients get public projections and use typed JSON-RPC methods, events, and callbacks. The app-server supports session discovery/history plus start/resume/continue and event re-synchronization. The protocol should be the only contract the app consumes; protocol catalogue/handshake and trust behavior should be checked against the pinned source when implementation changes.

Official feature references: [agents and subagents](https://docs.mistral.ai/vibe/code/cli/agents), [safety, approvals, and permissions](https://docs.mistral.ai/vibe/code/safety-approvals-permissions), [CLI session workflows](https://docs.mistral.ai/vibe/code/cli/work-with-cli), [skills](https://docs.mistral.ai/vibe/code/cli/skills), [hooks](https://docs.mistral.ai/vibe/code/cli/hooks), [connectors](https://docs.mistral.ai/vibe/code/cli/connectors), and [choosing CLI, VS Code, or web sessions](https://docs.mistral.ai/vibe/code/choose-cli-vscode-web-sessions). Session files remain Vibe-owned; use protocol projections for listing, history, and recovery.

**OpenCode: one backend contract can serve multiple clients.** Its V1 layout separates runtime/core, desktop, web app, TUI, JS SDK, and plugin API. The local server exposes an API and SSE event stream ([server docs](https://opencode.ai/docs/server/)); the [desktop package](https://github.com/anomalyco/opencode/tree/82ea3a3/packages/desktop) launches a bundled sidecar and drives it as a client ([desktop README](https://github.com/anomalyco/opencode/blob/82ea3a3/packages/desktop/README.md)). This validates the general process/UI split. Its monorepo, broad plugin surface, custom agent and permission system, and Bun/tooling scale are not a fit for this wrapper. Its [Windows guidance](https://opencode.ai/docs/windows-wsl/) recommends WSL for best compatibility, which weakens its value as a Windows-native blueprint.

**DeepSeek Harness: durable state and live events have different jobs.** Its [architecture](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15/docs/architecture.md), [agent-loop map](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15/packages/core/agent-loop/README.md), [session subsystem](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15/docs/subsystems/session.md), and [persistence design](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15/docs/subsystems/persistence.md) describe a canonical append-only session history alongside transient live events. Its Web client uses a host-owned state model and recovery/resync after stream gaps ([client architecture](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/web-client)). Its Electron desktop bundles an exact runtime and starts a local host ([desktop README](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15/apps/desktop/README.md)). These are useful principles for UI state and recovery. The full Cordis-based plugin substrate, event framing/checkpoints, and extensive subsystem architecture are not needed here; the project is explicitly a preview and changing quickly.

## Windows shell constraints

- [Electron's first-app guide](https://www.electronjs.org/docs/latest/tutorial/tutorial-first-app) uses Node/JavaScript/HTML/CSS. [Packaging](https://www.electronjs.org/docs/latest/tutorial/tutorial-packaging) still requires a Windows packaging/signing path, and bundling Chromium/Node costs installer size and memory. Keep local assets only, enable context isolation and renderer sandbox, restrict CSP, and validate IPC senders as described in the [Electron security guide](https://www.electronjs.org/docs/latest/tutorial/security).
- [Tauri 2 prerequisites](https://v2.tauri.app/start/prerequisites/) require Rust stable with the MSVC target, Visual Studio C++ Build Tools, and WebView2. Its [sidecar](https://v2.tauri.app/develop/sidecar/) and [shell permissions](https://v2.tauri.app/plugin/shell/) offer a controlled native process boundary, but Rust/Cargo are absent from the current machine.
- Prefer Vibe app-server stdio over opening a local TCP service: it avoids a port, auth, and CORS boundary. Use a narrowly scoped host-to-renderer bridge; do not put Vibe execution or credentials in the renderer.
