# Mistral Vibe desktop and local-session research

Research snapshot: **2026-10-12**. Upstream source is pinned to [`mistralai/mistral-vibe` `4ae5c5955da8e761318916bdb1a7f46f0b50c7d0`](https://github.com/mistralai/mistral-vibe/commit/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0), release **v2.26.1** (2026-10-09). The checkout was clean at that commit when inspected. Links to source below use that SHA unless a historical commit or release is named.

This audit distinguishes generally available products, reusable upstream source, rollout evidence, and conclusions inferred from those sources. It does not assume that an internal or staged Vibe Desktop is generally downloadable.

## Finding

Mistral’s upstream source confirms an active local desktop client lineage: the CLI README referred to **Le Chat Desktop** in August, and subsequent engine changelogs call it **Vibe Desktop**. The changelog says it can create local projects from existing folders, retain managed worktrees, expose Smart Approve in a rollout, and show unseen-session indicators. Those entries establish real desktop integration work, but the public product docs and v2.26.1 release assets do not establish a generally available, separately downloadable native Windows desktop app.

There is already a Windows desktop shell called **VibeZ**. Its public source describes a Rust/Tauri native shell around Mistral’s hosted Vibe website, rendered through the operating system webview (WebView2 on Windows). It is a valid desktop alternative for the hosted Vibe surface, so “first desktop app for Mistral Vibe” is not a credible product claim.

The defensible community-client opportunity is narrower: a **Windows-first, open-source local Vibe Code session manager** that runs the upstream app-server against user-selected local folders and worktrees, and treats upstream protocol conformance, safe session ownership, Windows packaging, diagnostics, and update compatibility as product features. It should reuse Vibe’s agent/runtime rather than implement a second agent. This still overlaps with official Vibe Desktop’s evidenced local-project and worktree work, so differentiation rests on public availability, Windows support quality, transparent compatibility, and community control—not feature novelty.

## What upstream source makes reusable

### `vibe-app-server` is the right engine boundary

The Python package publishes three entry points: `vibe`, `vibe-acp`, and `vibe-app-server`. The app-server runs JSON-RPC over stdio and delegates work to the same Vibe runtime/harness; its public method list covers session lifecycle, configuration, trust, reviews, connectors/MCP, background processes, and Git worktrees. The app-server was introduced as the typed runtime owner between delivery clients and the core engine rather than as an alternate agent implementation. [entry points and package metadata](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/pyproject.toml#L1-L8) · [stdio server](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/stdio.py#L34-L76) · [wire method registry](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/protocol.py#L108-L257) · [v2.23.0 release notes](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/CHANGELOG.md#L850-L856).

The UI can ask the server to list/read/start/resume/continue/fork sessions; receive state notifications; submit turns; inspect configuration and account state; request workspace trust; access review state; and manage worktrees. V2.26.1 adds `session/lease/subscribe` and a `lease_holder` projection so another client can present an externally held session as read-only. `events/read` is listed for protocol completeness but currently returns an intentionally empty batch; a reconnecting client should reconcile from session reads/lists rather than depend on replay. [dispatch and event behavior](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/server.py#L729-L805) · [lease response types](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/protocol.py#L446-L462) · [2.26.1 change](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/CHANGELOG.md#L8-L14).

The worktree API is substantial and should be delegated to the server: `workspace/git/worktrees/list`, `limit/update`, `prune`, `reap`, `reap/cancel`, and `remove`. Removal can inspect before action and reports whether the branch was created by Vibe, other holders, outcome, and reasons. `SessionWorktrees.resolve_for_start` owns session start/fork/cleanup behavior; the core lifecycle deliberately preserves a worktree if it is still held, dirty, untracked, unpushed, or otherwise unsafe to discard. [worktree routes](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/protocol.py#L247-L257) · [wire models](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/protocol.py#L1623-L1770) · [app-server worktree owner](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/_worktree_session.py#L64-L185) · [core cleanup](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/core/session/worktrees.py#L80-L175) · [Vibe’s cleanup rules](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/README.md#L1198-L1220).

The protocol is a client contract in source, not a frozen cross-version standard. Pin the engine, record its version/protocol handshake, and run client contract/conformance checks when upgrading. The official codebase’s `tests/app_server` and `client-e2e` are useful references for realistic scenarios. Avoid duplicating harness internals or calling private core classes from the UI.

### Runtime conformance findings

The declared protocol and the default runtime are separate evidence. The real
2.26.1 Unified Harness executes approved file writes and projects their effects,
but returns `method_not_found` for `review/state` and `review/turnDiff`. Those
methods are dispatched by the legacy Python handler; the default Unified adapter
has no review branch. The client reports this state and leaves review completion
to the upstream boundary. See the [executed validation](validation.md),
[legacy dispatcher](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/_handler.py),
and [Unified adapter](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/_unified_harness_backend_adapter.py).

### Important boundary: local projects versus cloud links

The engine’s `session/list` scopes saved sessions by `cwd`; the API has no method that catalogs arbitrary local folders as named desktop projects. `projectLinks/*` is for linking local roots to **Vibe Code Web** projects, and `vibeCode/projects/*` is cloud/teleport project selection. The upstream changelog says Vibe Desktop can create a local project from any existing folder, so the catalog/UX appears to be a client responsibility or a separate internal API not present in this public registry. **Inference from the current method registry and project-link implementation:** the community app should own only its local workspace catalog and let the server own session/harness state. [method registry](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/protocol.py#L108-L257) · [project-link contract](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/_project_links.py) · [local-project changelog entry](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/CHANGELOG.md#L505-L528).

### Authentication and provider ecosystem

The app-server setup surface contains only `setup/status`, `setup/store-credential`, and `setup/submit-choices`. Status returns resolved provider/model/base URL/theme, `supports_browser_sign_in`, and a boolean `has_api_key`; the key is never returned. Store-credential delegates to Vibe’s persistence path and reports success or a save error. It uses the configured provider and the server’s own key resolution rather than asking the UI to edit `.vibe` files directly. [setup routes](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/_setup.py#L53-L119) · [setup wire types](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/app_server/protocol.py#L1849-L1885).

There is **no browser sign-in start/complete method in the app-server method registry**. The Python onboarding service implements PKCE browser sign-in against `/vibe/sign-in`; the Rust CLI also has an internal port and stores the returned API key through `setup/store-credential`. That is reusable source, but not a UI-level RPC contract. A first client can support API-key paste/store using the server setup methods; native browser sign-in needs an intentional bridge/port or delegation to upstream onboarding. Do not make the renderer independently persist credentials. [Python browser-sign-in service](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/setup/auth/browser_sign_in.py#L78-L103) · [PKCE endpoint](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/setup/auth/http_browser_sign_in_gateway.py#L83-L120) · [Rust CLI auth source](https://github.com/mistralai/mistral-vibe/tree/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/cli-rust/src/setup/auth).

Vibe supports Mistral credentials and configurable providers. Official docs also support a fully local or OpenAI-compatible model endpoint (including vLLM, llama.cpp, LM Studio, and Ollama); a Mistral account is not required for that path. The Python package requires Python 3.12+ and pins `mistralai==2.6.0` at this snapshot. The key persister prefers the OS keyring and falls back to Vibe’s `.env` file. [offline/local models](https://docs.mistral.ai/vibe/code/cli/offline-models) · [package metadata/dependencies](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/pyproject.toml#L1-L8) · [SDK pin](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/pyproject.toml#L68-L74) · [key persistence](https://github.com/mistralai/mistral-vibe/blob/4ae5c5955da8e761318916bdb1a7f46f0b50c7d0/vibe/setup/auth/api_key_persistence.py#L217-L248).

## Differentiation and gap decisions

| Candidate claim or feature                                | Decision                                           | Reason                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| “First Mistral Vibe desktop app”                          | **Reject.**                                        | VibeZ ships Windows installers; upstream changelog confirms official Vibe Desktop rollout.                                                                                                                                                                                                                 |
| “A desktop wrapper for Vibe”                              | **Reject as the thesis.**                          | VibeZ already provides a native shell for the hosted Mistral site. A thin WebView wrapper gives little new value.                                                                                                                                                                                          |
| Windows-native local sessions through upstream app-server | **Keep as core thesis.**                           | Local CLI and VS Code exist, but official Windows support is limited and they are not standalone workspace managers. Vibe Code Web is remote/cloud. A focused Windows client can integrate local folders, process/session ownership, event handling, and Git worktrees without reimplementing the harness. |
| Worktree and safety UX                                    | **Keep, with protocol delegation.**                | Worktree list/inspect/reap/remove, dirty-state and external holder data are already exposed. The opportunity is to render and test these semantics well, not create competing cleanup logic.                                                                                                               |
| Open-source portability and compatibility reporting       | **Keep as durable differentiators.**               | Official Desktop may reach Windows; source pinning, visible engine version, automated protocol conformance, release notes, and upstream-compatible fallbacks make the community client useful even then.                                                                                                   |
| New model/API integrations                                | **Do not prioritize.**                             | Vibe owns provider configuration, Mistral SDK usage, local OpenAI-compatible support, model selection, and auth. A second provider layer duplicates maintenance.                                                                                                                                           |
| Browser sign-in parity on day one                         | **Defer until an intentional auth bridge exists.** | The public RPC does not expose the PKCE flow. API-key setup/storage is available through upstream RPC; Python/Rust internal source can inform a later port.                                                                                                                                                |
| Named local project catalog                               | **Client-owned, minimal.**                         | Current API scopes sessions by working directory and has cloud project links, not a local project CRUD catalog. Store only recent folder roots and display names; defer agent state to Vibe.                                                                                                               |
| Claim of feature superiority over official Desktop        | **Avoid.**                                         | Official release notes already describe local-project, worktree retention, approval-mode, and unread-session UI features. The defensible distinction is transparent community maintenance and quality of Windows/app-server integration.                                                                   |

Local smoke evidence from the canonical 2.26.1 runtime: initialization, setup status, session listing, and workspace trust calls succeeded; `session/start` without credentials returned a typed unauthorized error. This confirms the basic Windows app-server boundary and that missing credentials must be handled as a setup state.

## Evidence classes and open points

- **Available now:** Vibe CLI on Windows (with the upstream UNIX-target caveat), Mistral Vibe VS Code extension, cloud Vibe Code Web, Work/web/mobile, VibeZ 3.0.5 Windows installers, and the upstream app-server entry point in the Python package.
- **Reusable in source:** typed JSON-RPC app-server, Unified Harness/runtime bundling code, local session APIs, safe worktree lifecycle, trust, configuration, review, connector/MCP, API-key persistence, internal browser sign-in implementations.
- **Explicit rollout evidence:** official Vibe Desktop local projects, managed worktree retention, Smart Approve picker, and unseen-session indicators in dated engine changelog entries.
- **Inferred from source:** the official desktop’s local folder catalog is not part of the public app-server method registry; the client likely owns this local project catalog. The VibeZ architecture is a hosted-site wrapper rather than a local app-server integration because its README describes embedded website/WebView content and not a local engine connection.
- **Unconfirmed:** a public Mistral-branded standalone Windows Vibe Desktop installer, general availability, OS support matrix, browser-auth RPC for external clients, versioned stability guarantees for app-server, and whether official Vibe Desktop will expose its client implementation.
